# Agentic GRC delivery — 2026-11-24

The GRC operator needs to move from a cited answer to a bounded, inspectable action, assess a regulatory change against current policy/control records, and govern real AI system dependencies and newly discovered tools. Extend the existing Ask Fornost, Regulatory Center and AI Governance workspaces; preserve TR/EN, themes, native records, privacy routing and independent approval gates.

## Acceptance

- Ask Fornost queries current Risk, Asset, BIA, Control, Evidence, Vendor, KRI, Findings and AI records. Answers expose source codes and bounded coverage, including offline operation. Model output is advisory and cannot choose arbitrary SQL/API calls.
- Supported commands propose overdue-finding reminders and asset-linked risk drafts. A server-owned expiring proposal pins exact parameters and source revisions. Only the requesting authorized user can explicitly apply it. Stale, changed, expired, replayed or unauthorized requests cannot produce extra writes. Business writes and `Ask Fornost (Kullanıcı Onaylı)` audit receipts commit together. Reminders are internal work items, not external email/messages.
- Regulatory analysis uses the stored change text plus current published approved policies and controls. Outputs preserve source excerpts, distinguish missing coverage from verified non-compliance, show workload estimates with explicit assumptions, and create only draft policy versions/open CAPA through explicit human actions. Published versions and independent review remain intact.
- A five-question EU AI Act screening records answers, legal source/version, reasoning and applicable checklist. Unknown answers and potential exceptions require review; it never grants legal compliance or production approval. Classification escalations update the governed profile; native production approval guards reject unresolved screening, incomplete checklists and unsafe declared write permissions.
- AI BOM records model/vector store/MCP/API nodes, explicit permissions, data boundary and HITL points. Map shows declared permissions, not a claim of live enforcement. Changes revoke stale review, record history and never probe/execute endpoints.
- Shadow discovery parses bounded OAuth/SSO/network/spend exports, identifies candidates from transparent rules, cross-checks approved inventory, previews before import and deduplicates on stable source identity. A match is a candidate, not a proven unauthorized application. Existing queue handles admission/ban decisions.

## Validation and release

Transactional service/route tests cover role isolation, tampering, staleness, idempotency, rollback, SoD, classification boundaries and CSV handling. A production-artifact browser workflow covers both Ask entry points, card approval, policy/CAPA draft conversion, five-step wizard, BOM map and Shadow import in TR/EN light/dark at desktop/mobile sizes. Run normal lint/typecheck/build, migration and regression checks. Release under the existing main/live authorization after validation; verify exact production revision. Additive migrations permit application rollback without destructive schema changes. Customer provider connectivity remains customer-configured. No external messages or customer credentials are required.
